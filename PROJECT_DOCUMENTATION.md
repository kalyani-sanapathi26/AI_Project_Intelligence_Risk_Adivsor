# AI Project Intelligence & Risk Advisor
## Technical Project Documentation

## 1. Project Overview

**AI Project Intelligence & Risk Advisor** is a Python-based project intelligence application built with Streamlit. It is intended to help users review project information, analyze scope, identify risks and blockers, assess project health, ask questions about project documents, and prepare structured project documentation.

The application brings project-document processing and AI-assisted analysis into one interface. Its output depends on the project documents provided, the configured language-model provider, and the analyses successfully generated by the application.

## 2. Problem Statement

Project information is often spread across requirements, sprint updates, task lists, risk registers, and other documents. Reviewing these sources manually can make it harder to find dependencies, understand blockers, identify delivery risks, and prepare consistent status reports.

This project aims to provide a single interface for processing project documents and turning relevant project information into useful analysis and summaries.

## 3. Project Objectives

- Process project documents and prepare their content for retrieval.
- Answer questions using relevant project context.
- Summarize project scope, objectives, requirements, deliverables, and milestones when supported by the available information.
- Identify and explain project risks and blockers.
- Assess project health using the application's configured health dimensions.
- Present project insights in a dashboard.
- Generate structured documentation for review and sharing.

## 4. Key Application Modules

### 4.1 Document Processing

The Documents module accepts project documents and processes their content for downstream analysis. The exact formats supported depend on the current document-loader implementation and installed dependencies.

### 4.2 Retrieval-Augmented Generation (RAG)

The RAG workflow retrieves relevant content from indexed project information and passes that context to a language model to formulate an answer.

Typical conceptual workflow:

1. A user submits a project-related question.
2. The application retrieves relevant document chunks.
3. Retrieved context is provided to the configured language model.
4. The generated response is shown to the user.

The reliability of a response depends on the quality and relevance of the source documents and retrieved context.

### 4.3 Project Scope Analysis

This module presents project scope information such as objectives, requirements, modules, deliverables, and milestones when these details are available in the project sources.

### 4.4 Risk Analysis

The Risk Analysis module reviews project information to identify delivery or execution risks. Risk descriptions, severity, impact, ownership, status, probability, and mitigation actions should only be presented when supported by source information or explicitly produced by the analysis logic. Missing values should not be represented as verified facts.

### 4.5 Blocker Analysis

The Blocker Analysis module identifies issues or dependencies that may prevent work from progressing and presents relevant actions where available.

### 4.6 Project Health Analysis

The Project Health module evaluates project condition using configured dimensions, including scope clarity, progress, timeline/delivery, risk management, and blocker management. It presents an overall health score and status based on the application's scoring logic.

### 4.7 Documentation Generation

The Documentation module prepares a structured project document with four sections:

1. User Stories
2. Risk Register
3. Action Items
4. Project Summary

The content should be reviewed for accuracy before it is used as an official project record. Download options depend on the current application implementation.

### 4.8 Dashboard

The Dashboard provides a consolidated visual view of available project insights. The exact charts, counts, filters, and download options depend on the data available and the current implementation.

### 4.9 AI Project Assistant

The AI Assistant provides a conversational interface for asking questions about project information. Responses depend on the context available to the assistant and the configured language-model provider.

## 8. Installation and Setup

### Prerequisites

- Python installed on the computer.
- Git installed to clone the repository.
- Access to the configured language model, such as an API key for a cloud provider or a working local Ollama model.
- All dependencies listed in `requirements.txt`.

### Step 1: Clone the repository

```bash
git clone https://github.com/kalyani-sanapathi26/AI_Project_Intelligence_Risk_Adivsor.git
cd AI_Project_Intelligence_Risk_Advisor
```

**Note:** The repository URL and folder name may differ slightly. If the cloned directory has a different name, use the actual directory name shown by Git.

### Step 2: Create a virtual environment

```bash
python -m venv venv
```

Activate it on Windows Command Prompt:

```bat
venv\Scripts\activate
```

Activate it on Git Bash:

```bash
source venv/Scripts/activate
```

### Step 3: Install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### Step 4: Configure the language model

Set up the environment variables required by the provider you plan to use. If the application uses a `.env` file, create it locally and follow the variable names expected by `src/llm.py`.

**Never commit `.env`, API keys, access tokens, or other secrets to GitHub.** Keep them excluded in `.gitignore`.

### Step 5: Start the application

From the project root, run:

```bash
python -m streamlit run app.py
```

Open the local URL printed by Streamlit in your browser.

## 9. Typical Usage Workflow

1. Start the Streamlit application.
2. Open the Documents module and upload the available project files.
3. Process the documents so their content can be used by the analysis workflow.
4. Ask document-based questions in the RAG Pipeline or AI Assistant.
5. Review project scope, risks, blockers, and project health.
6. Review the dashboard for a consolidated view of available results.
7. Generate the four-section project documentation.
8. Review generated results for factual accuracy before sharing or downloading them.

Some analyses may depend on prior document processing or on other analysis results. Follow the current interface prompts if a module indicates that required information is not yet available.

## 12. Validation and Responsible Use

- Check that uploaded documents contain the intended project information.
- Review AI-generated risks, recommendations, and summaries before making project decisions.
- Do not assume an unreported probability, owner, date, or status.
- Treat generated documentation as a draft until reviewed.
- Avoid uploading confidential or sensitive project data unless permitted by the applicable policy.
- Do not commit API keys, private credentials, virtual environments, or generated local databases unless the project explicitly requires and safely manages them.

## 13. Limitations

- Output quality depends on the completeness and clarity of the source documents.
- Retrieval may miss relevant information if documents are poorly structured or the right text chunks are not retrieved.
- Language models can produce incorrect or unsupported statements; human review remains necessary.
- Provider quotas, network access, model availability, and local configuration can affect AI features.
- Dashboard metrics are only as reliable as the underlying extracted and analyzed data.
